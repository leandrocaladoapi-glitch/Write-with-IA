## Opening hook

The horror story every writer eventually lives: it is 1 a.m., three weeks after the best chapter you've ever written — the chapter that finally *earns* the ending you've promised since Chapter 1 — and the document in front of you says the last save was sometime before you experimented with "the version where the sister stays." You remember dragging files around. You remember a prompt window where the assistant returned a rewritten chapter you accepted on the spot. You remember, distantly, closing something that asked "Save changes?" You open the backup folder: same timestamp. The cloud sync: same timestamp. The chat history: forty pages of prompts, and somewhere in there the chapter — but which paragraph was v1 and which was the machine's take you meant to rewrite?

You did not lose the chapter because you lack talent. You lost it because *project structure was optional until it was fatal* — and AI-assisted writing multiplies the risk: every accepted generation is a fork you might want back, every chat session is fragmentary memory pretending to be the real thing. The fix is unglamorous and completely reliable: **a folder anatomy, a versioning rule, a story bible, and a session rhythm** — fifteen minutes of setup that turns months of AI-assisted drafting from archaeological dig into clean commit history. This chapter installs all four, live, using Example A's project as the specimen, and by the end your Project folder will exist with a real Draft 1 inside it.

## Learning objectives

By the end of this chapter, you will be able to:

- [ ] Set up the book's project folder anatomy for your story.
- [ ] Version drafts with numbering plus changelogs.
- [ ] Maintain a story bible and a session log.
- [ ] Run sustainable writing sessions with AI chat history as project memory — and its limits.

## Project folder anatomy

One folder per story. Inside it, five subfolders and two loose files — the complete anatomy used everywhere in this book:

```text
my-story/
├── manuscript/        # the book itself — numbered drafts only
│   ├── draft-01.md
│   ├── draft-02.md
│   └── ...
├── bible/             # story bible + character sheets (Ch 3, below)
├── research/          # fact sources, policy notes, period detail
├── prompts/           # your prompt cards + tested variants (Ch 6)
├── cuts/              # everything you delete from the manuscript
├── changelog.md       # what changed between drafts, one line each
└── session-log.md     # what you did when, for how long, next step
```

The rules that make the anatomy work are simpler than the tree:

- **`manuscript/` holds numbered drafts only — and the current number is always complete enough to compile.** `draft-03.md` is a *whole* manuscript (however rough), not a scratch file. You never edit an old number in place; a new draft number is minted when a meaningful revision completes (the pass system of Chapter 12 defines "meaningful" precisely). Working fragments — scenes in progress — live inside the current draft or in clearly named work files (`wip-ch09-kitchen.md`) that get *folded in* before any new number is minted. The invariant: at any moment, you can hand someone `draft-current` and they can read your story start to finish.
- **`cuts/` is non-negotiable, and it changes your psychology.** Every paragraph, scene, and subplot removed from the manuscript gets pasted here with a date line — because the real reason writers fail to cut ("but what if I need it later") is that "later" has nowhere to live. A cut with an address stops being a loss. AI-assisted drafting *increases* cuts (faster generation → more surplus → more deletion), so the folder starts on day one, not when you first feel brave. Naming convention: `2026-09-24-ch03-mothers-letter-scene.md` — date, origin, content; the origin tag matters when you're mining cuts in Chapter 12.
- **`prompts/` and `research/` are where trustable references accumulate.** Prompt cards from Chapter 6 (yours *and* the book's copies you've tested); research notes with their sources and dates (Appendix E's protocol at personal scale: source, date accessed, one line of what it supports). When Chapter 15 asks you to re-verify a policy, the folder is the checklist.
- **Loose files live loose on purpose:** `changelog.md` and `session-log.md` sit at root because they apply to *every* draft and *every* session — filing them would hide them, and hidden logs die.

**Tool-agnostic by design.** This anatomy is folders and markdown; any editor can open it; any sync tool can carry it; any model can be pasted from it. If you live in a word processor instead, mirror the structure (documents named `draft-03`, a `Cuts` document, a `Changelog` document) — the *invariants* are what matter: numbered complete states, addressed cuts, one-line change history. Named products come and go (Chapter 5's dial #5); your project should outlive any of them.

If the story doesn't exist yet, create it from your Chapter 2 skeleton — the skeleton *is* draft material, and a project folder with one page already beats a brilliant idea in a notes app. Three minutes; do it before finishing this page's section headings.

## Versioning without tears

Versioning sounds bureaucratic and behaves like insurance you're *grateful* for the first time a revision goes sideways. The whole system is two habits:

**Habit 1 — Draft numbering.** `draft-01`, `draft-02`, forward only, integers never overwritten. When is a new number minted? When a *coherent state change* completes: all scenes of a pass applied (Chapter 12's structure pass done → `draft-04`), a milestone redraft of Part Two folded in, beta feedback from a full round integrated. Not minted: mid-sentence saves, every session, or the machine's raw output (that's FILL material, not a draft). Inside a number, your editor's autosave does what it likes — the *number boundary* is the granularity of memory. Typical novella rhythm: `draft-01` (first end-to-end draft) → `02` (self-edit structure) → `03` (character pass) → `04` (first beta round) → `05` (line pass) → `06` (final proof state). Six states for a whole novel is normal; twelve means passes are being split into slivers (resist — see Chapter 12's non-convergence pitfall); one means you're flying without instruments.

**Habit 2 — The changelog, one line per mint.** Format: `- draft-03 → 04 · 2026-09-24 · structure pass: cut subplot B, moved storm arrival from ch6 to ch4; notes: [link/decisions-file range]`. The line answers *what changed and why* in under thirty seconds of future reading — and the `notes` hook points at the adjudication trail (decisions file, pass log) where the *full* why lives. Three changelog payoffs compound across a project: **reversibility** (a bad revision direction is discovered at draft-05? You can see exactly what draft-04→05 did and selectively restore — no archaeology); **rhythm awareness** (skim the log; if every entry says "polish," you're Chapter 12's F-07 case); and **authorship evidence** (dates + descriptions of your human adjudications; Chapter 15 will point back here as the kind of process record that documents *your* authorship — keep it factual and unhyped).

One AI-specific guard: **machine outputs never mint drafts.** The assistant's chapter rewrite is a proposal; it lives in the chat and then (if worth keeping) as a file in `wip-` space or a cut — the number advances only when *you* have integrated, edited, and accepted the state as a readable manuscript. This single rule prevents the worst AI-versioning pathology: a manuscript folder where you can no longer distinguish your prose from generations you never actually reviewed.

> CRAFT NOTE — "But git does this better." Version control tools *do* exist and writers do use them; they are also a hobbyist tax for this audience — the mental model (numbered states + one-line logs + never overwrite) is the transferable skill, and the simple system is the one you'll still run at 11 p.m. after a full day of work. If you already speak git fluently, use it, and keep this book's changelog anyway: your future self reads lines, not diffs. The failure mode to avoid isn't choosing plain files — it's *choosing nothing*.

## The story bible

The **story bible** is the project's long-term memory: a single reference document (or small folder of documents — `bible/` can hold `characters.md`, `setting.md`, `timeline.md` once it grows) containing the facts every later stage must *not* re-invent. For AI-assisted work specifically, the bible has a doubled role: it's what *you* consult for continuity, and it's what gets **restated onto the model's desk** at the start of fact-dependent tasks (Chapter 5's shared-desk rule — the bible is the antidote to macro-amnesia). Bible-first prompting — leading continuity, critique, and drafting tasks with the relevant bible extract — is the practice Chapters 9–12 will lean on constantly; it starts with having a bible worth pasting.

**The template** (starter scale — grows by section, not by guilt):

```text
STORY BIBLE — [title]                          v[__]  updated: [date]

1. PREMISE & STAKES: the Chapter 2 skeleton, kept current (paste it).
2. CHARACTERS: for each — the Ch 3 sheet (or cut-down cast version).
   One line each for walk-ons: name · function · one trait.
3. TIMELINE: story-internal order of events with day markers;
   real-world anchors only where needed (seasons, dates, ages).
4. SETTING FACTS: place rules that must never contradict — geography,
   institutions, technology/magic limits (Ch 4's constraints), names
   and spellings (THE canonical spellings list — the single most
   consulted section you will ever maintain).
5. STORY RULES: what this story promises and forbids (no one lies
   off-page? POV never leaves Mara? the storm is never comic?) —
   the constraint packs from Ch 6 hang here.
6. OPEN THREADS: unresolved seeds with the chapter planted and the
   chapter intended to pay off — the cheapest late-book insurance
   there is.
7. DECISIONS LEDGER: pointer to the decisions file + the five
   decisions most likely to be second-guessed, with their one-line
   why.
```

**Maintenance rhythm beats maintenance zeal.** Update the bible *at draft-number minting* (new number → ten-minute bible sync) and whenever a *fact* changes mid-session (the storm moved → timeline line updated *before* you close the editor). The failure mode isn't a bible that's briefly stale; it's a bible that's *selectively* stale — half-current facts are worse than none, because you and the model will both trust them (F-06's internal cousin: confident contradictions against a document that used to be right). If a fact appears in a draft but not in the bible, the bible is wrong *by definition* until synced — the manuscript is canon; the bible is the index; the loop closes at every mint.

## Sessions that compound

Structure supports the folder; **rhythm** supports the writer. Three session mechanics, tuned for AI-assisted work specifically:

**Session skeleton (the twenty-second version).** Open → *reread the last 500 words* (orientation, always — even when you wrote them an hour ago) → *state today's one outcome in one line at the top of your notes* ("kitchen scene drafted; bible synced") → *work* → *close with the session log filled and the next step written*. That last line is the whole trick of sustainable practice: **end every session mid-sentence or with the next sentence specified**, so tomorrow's start has zero decision cost. AI sessions add one step: before closing a productive chat, *harvest it* — copy the accepted output to `wip-`, paste the prompt that worked into `prompts/` (if reusable), one decisions line if substantive. Chats are workshops, not warehouses; harvest or lose.

**Session log format** (`session-log.md`, one block per session — this exact shape feeds Appendix F habits too):

```text
## 2026-09-24 · 07:10–07:55 · words: +840 (draft-03 @ 41,200)
Goal: draft kitchen confrontation from beats 4–6.
Mode: voice-anchor co-draft (PC-01 v2) → hand rewrite ~50%.
Adjudications: 2 accepted (deadline fact, doorway image), 5 rejected
  (generic summaries — see decisions 014–018).
Bible: timeline synced (storm = day 2); no new names.
Next: Theo's reaction scene — start from "the wrong kind of clean".
Blockers: none | fog: mild — resolved by beat list.
```

Counting words: **total at session end minus session start**, pasted at the left — thirty seconds, no app. Word counts are *instrumentation, not targets* (Chapter 16's 90-day plan converts them into targets deliberately; during learning stages they only answer "am I moving?"). Log them anyway, because the log's real payload is the *Mode* and *Adjudications* lines: those entries are how you'll later answer Chapter 14's comparison question ("what does my accepted-AI prose actually cost me?") and how you'll notice drift patterns ("last six sessions: mostly rejected expansions — I'm over-generating").

**Chat history as project memory — and its limits.** It's tempting to treat your chat threads as the project's second brain: they contain decisions, experiments, tone calibration. They are a *supplementary* memory with three hard limits: (1) **searchability is poor** — threads don't query well, and platform retention can change under you (Chapter 5's policy hygiene); (2) **it's raw** — chats mix accepted work, rejected experiments, and machine fluff with no adjudication markers; (3) **it's not portable** — your project must be reconstructable from *your folders alone* if the tool disappears tomorrow. The working policy: **hubs and spokes** — folders are the hub (canon: drafts, bible, logs, harvested prompts); chats are spokes (live workshops). Anything that matters gets *promoted* to the hub at session end (the harvest step). If you catch yourself about to ask a chat "what did we decide about Theo's scar?" — that's the bible failing its job; answer from the hub, then fix the hub.

> REALITY CHECK — No setup survives contact with enthusiasm *or* avoidance: the two setup failures are the perfectionist (seven days tuning folders, zero words — the pitfall below) and the romantically disorganized (brilliant sessions, no memory — the hook's 1 a.m. self). Both fail the same invariant: *could a stranger (or future you) reconstruct the story's state in ten minutes?* Everything above — numbers, logs, bible, harvest — serves only that question. If your current setup can't pass it this week, retrofit the invariants; don't redesign the aesthetics.

### Session architectures that survive real life

The session skeleton fits *inside* a session; these three patterns arrange whole weeks — pick by your actual life, not your fantasy one, and re-check at Chapter 16's 90-day plan:

**Pattern A — Maker's morning (best for drafts-in-motion).** Writing block first, before email and chat: orientation read (5 min), one outcome stated (1 min), drafting or co-drafting with anchors (40–90 min), harvest + log + next-sentence line (10 min), *then* the rest of the world. The AI chats open only after the day's outcome sentence is written — chats are tools serving today's line, not morning entertainment that pre-loads the desk with everyone else's priorities (Chapter 5's shared desk applies to *your* attention too).

**Pattern B — Split-shift (jobs, caregiving, fragmented days).** Two labeled halves: a *maker* half (≥35 uninterrupted minutes — drafts, anchors, hand rewrites only) and a *manager* half (prompts prepared, continuity checks, bible sync, prompt-file filing, harvest cleanup). The iron rule: **manager work never happens inside maker time**, and maker work never starts with a chat — you may open a session *mid-scene*, but the first keystroke is yours. On days with only a manager half: prep beats (write tomorrow's FILL-B beat list), sync the bible, mine cuts — project-forward motion without pretending fragmented minutes are drafting minutes.

**Pattern C — Weekend batch (the one-weekend-a-week life).** Saturday = generation day (bible review, prompt prep, 2–3 co-drafted scenes with full anchors); Sunday = adjudication day (rewrite passes, compliance grading, changelog/bible sync, next weekend's beat prep). Generation and adjudication on different days is the secret structure: it guarantees the *human pass* always has fresh eyes, and it makes drift visible (Sunday's rewrites accumulate into a pattern you can actually see across one week's output).

All three share the invariants: one outcome line per session, harvest before close, next-step always written, drafts minted only at coherent boundaries. What varies is *when* chats open and *when* adjudication happens — decide that once, write the pattern name in your session log's header, and let the log's consistency do the coaching. If two weeks of blocks show the chosen pattern never actually firing (zero maker blocks logged), the pattern was cosplay: downgrade honestly (three 35-minute maker blocks beat two fantasy Saturdays) rather than keep aspirational architecture that trains you to distrust your own logs.

### The three audits your logs unlock

Logs are only romantic in the abstract; concretely they exist to run three cheap audits — schedule them or they won't happen:

1. **Weekly rhythm audit (10 minutes, end of week).** Skim session blocks: maker blocks vs. manager ratio; average words *per maker block* (not per calendar day — honest denominators); most common blocker; one log line of adjustment ("manager work crept into mornings — move chats after the outcome line"). The audit's output is *one* change for next week. Multiple simultaneous fixes are how systems die.
2. **Adjudication audit (at every draft mint, ~15 minutes).** Tally decisions-file rows since last mint: accepted/rejected ratio, and the *categories* of acceptances (structure? deadline facts? description expansions?). Two failure signatures to hunt: acceptances clustering in a category you never intended to delegate (usually description — the machine's easiest sell), or a rejection rate so high you're acting as a full-time copy desk for a generator you don't need (trim the generation mode — Chapter 10's mode table will help you choose better modes per scene type).
3. **Voice drift spot-check (monthly, 20 minutes).** Pull three AI-assisted paragraphs and three hand-written ones from the current draft; read them cold, unlabeled: can you *reliably* tell which is which? If not — especially if the machine's are the ones you'd sign — Chapter 14's diagnostic and Chapter 10's anchor discipline need tightening *now*, while the sample is small. This audit is the early-warning system for the book's central risk (F-09 voice erosion); it takes twenty minutes a month because the logs already point at where the samples live.

None of these audits is a report card — they're instrumentation readings. The session log, changelog, and decisions file are the project's instruments; the audits are simply *scheduled glances at the dials*. Un-glanced instruments drift into decoration, and decoration is how the 1 a.m. hook happens twice.

### Backups: one paragraph, no hobby

The versioning system above protects you from *your* revisions; backups protect you from *everything else* — disk death, sync bugs, the coffee, the account lockout. You need exactly one paragraph of policy, not a homelab:

- **3 copies, 2 different places, 1 of them off-site** (the classic 3-2-1, compressed): your project folder lives on your machine (copy 1) and in *two* independent targets — a synced drive or cloud folder (copy 2, also your off-site via provider redundancy) and a periodic plain zip dropped on *any* second service or an external drive (copy 3, different technology). Automate the zip if you can (weekly, named `my-story-backup-YYYY-MM-DD.zip`), manual if you can't — a calendar reminder Friday at 17:00 is automation enough.
- **When:** backups run *at every draft mint* (numbered states compress perfectly) plus weekly during active drafting. Mint-and-backup become one ritual: change log line → zip → sync; three minutes, end of session.
- **Test once a quarter:** open one random old backup and *read a file*. A backup you've never restored is a rumor.

That's the whole topic. Provider-side sync is *not* a backup (it faithfully mirrors deletions and ransomware alike), which is why the periodic zip exists separately — and why `cuts/` gets backed up with everything else: your deletions are history too.

### Naming everything, once

Ambiguity in filenames compounds into archaeology; five conventions end the category:

| Thing | Convention | Example |
|---|---|---|
| Drafts | `draft-NN` forward-only, zero-padded | `draft-03.md` |
| Work-in-progress files | `wip-chNN-topic` | `wip-ch09-kitchen.md` |
| Cuts | `YYYY-MM-DD-chNN-topic` | `2026-09-24-ch03-mothers-letter.md` |
| Prompt cards | `PC-NN-slug` + version line inside | `PC-01-scene-drafter.md` |
| Backups | `my-story-backup-YYYY-MM-DD.zip` | `…-2026-09-26.zip` |

Plus two spelling decisions that pay for themselves the day a continuity check runs: **canonical spellings live in the bible's section 4** (the list is the single most-pasted bible section during AI sessions — every drafting prompt that names a person or place pastes from it), and **file names use ASCII hyphens and lowercase-with-hyphens** (portable across every tool you'll ever sync through). Write the table at the top of your changelog if you like; five lines consulted twice a week is cheap insurance against the "which file is current?" species of the lost-draft story.

### FAQ from the workshop floor

*What if I already have a messy project mid-story?* Retrofit, don't restart: compile the current state as `draft-01`, dump everything ambiguous into `cuts/` or `wip-`, write a changelog line "baseline import from disorganized state," paste what's decided into a starter bible, and adopt conventions going forward. Retroactive perfection is tooling procrastination in a trench coat; *forward* hygiene is the whole requirement.

*Should the bible be one file or many?* Start one file until it exceeds comfortable scrolling (roughly a novella's worth of sections filled), then split by section groups (`characters.md`, `setting-timeline.md`, `rules-threads.md`) with the premise/skeleton staying in the root file you paste most. Split when retrieval hurts, not before — three files to find one name is its own black hole.

*Where do worldbuilding *experiments* live — the 4,000-word history?* `research/` as `world-lore-draft.md`, clearly labeled *non-canonical until promoted*. The bible holds what the *story* has decided (Ch 4's worldbuilding-on-need discipline); the research folder holds the museum; promotion to bible = the lore earned a scene.

*Do I log AI sessions in the chat tool's own history features (projects, pinned threads)?* As *convenience*, never as structure — pins break, exports change, retention policies move (Ch 5). The hub's `prompts/`, harvests, and session-log pointers are the durable layer; treat every in-tool organization as a temporary desk arrangement you'd be fine losing tonight.

Read section 5 twice: **the story rules are Chapter 6's constraint packs lifted to project altitude** — "no one says closure" graduated from a prompt line to a canonical promise, because rules that only live in one prompt die with that prompt. Section 6's scar entry shows the loop closing *both ways*: Ch 4's prose and the bible agree today; Chapter 12's PC-22 continuity pass will machine-check that they still agree at draft-04 — the bible as shared source of truth for you *and* the assistant. And note what's deliberately empty (`research/sources.md`: present, seeded, waiting): the anatomy values *slots existing* over slots being full — an empty named shelf still tells you where tomorrow's fact belongs, which is half of why structure beats memory.

The setup took under an hour including transcribing the skeleton and sheet. The changelog has one line; the log has one block; Draft 1 exists. Everything in Part III — every prompt that says "according to the bible," every continuity check, every changelog mint — runs on *this*, which is why this chapter came before the workflow chapters: you cannot bible-first prompt a bible that isn't there.

## Exercises

- **Try (15 min):** Create your project's seven items (folder tree, empty `changelog.md` with a header, `session-log.md` with one template block) and name your Draft 1 — even if Draft 1 is your Chapter 4 milestone story, your skeleton plus three scenes, or a single compiled opening. If nothing exists yet, draft-01.md contains the skeleton and a title page: *it exists*. The invariant to pass: a stranger opening `manuscript/draft-01.md` can start reading your story today.

- **Stretch (1–2 h):** Fill a starter story bible for your real project: paste your Chapter 2 skeleton into section 1; add cut-down sheets for your two central characters (Chapter 3's fields); start sections 3–6 with everything currently *decided* (timeline may be partial; names list is mandatory — canonical spellings today save three continuity fixes later); section 7 points at your decisions file with five pinned calls. Time-box: ninety minutes max — a starter bible that exists beats a complete bible that doesn't; it syncs at every future mint. Then run one **mock AI session** against it: paste the bible's relevant extract + Chapter 4's POV decision into a fresh chat and ask for a 150-word continuation of any open beat — not to keep the output, but to feel what bible-first context *does* to response quality compared with your old bare prompts.

- **Project (ongoing):** Log every session for two weeks, no exceptions — the full block format, including Mode and Adjudications (three words suffice on dead days: "edited by hand, no AI"). At day fourteen, review the pattern, not the prose: Which modes recur? What's your real words-per-session distribution (your *actual* capacity, not your fantasy — Chapter 16 builds the 90-day plan on this number)? Where do sessions habitually end (blockers column)? Write ten lines of findings in the log's header. Two weeks of honest instrumentation is worth more than any productivity system you could buy, because it's *yours* — and if the findings scare you slightly, good: the 90-day plan needs truth, not aspiration.

## Pitfalls

> PITFALL — **Tooling procrastination.** *Symptom:* the folder system grows furniture while the manuscript doesn't — six color-coded subcategories per folder, a template for the templates, an evening spent comparing editors instead of drafting; the changelog's most active document is itself; genuinely useful setup work becomes the procrastination it was meant to enable. *Why it happens:* setup feels like progress (it is progress — visible, finite, low-risk) while drafting feels like exposure; when fear of the draft rises, the organism reaches for organizational nesting. Also feeds on AI-era novelty: a new tool promising to "manage your AI writing workflow" arrives, migration becomes the week's project. *Fix:* the **"setup done in one session" rule** — anatomy created, Draft 1 named, bible starter pasted, log seeded, *closed*: total ninety minutes, timer enforced; after that, any folder-shaped impulse gets written as a one-line to-do in the session log ("organize prompts subfolder") and executed *only* at session end, max ten minutes, never at session start. *Prevention:* the invariant question (can a stranger read draft-01 today?) is the *ceiling* of required structure, not the floor — anything beyond the ceiling that doesn't serve that question is furniture. Migration policy: new tools import the existing folder tree *as-is* or not at all; your project is the folders, and tools are tenants.

Related failure for Appendix C: adjacent to F-07's family — setup-shaped non-convergence (systems that keep revising themselves instead of the book); prevention is the same done-criteria instinct, applied to infrastructure.
